Guia do Prontuário LORD

Sistema web de prontuários eletrônicos da Liga Odontológica de Reabilitação e DTM, com ditado estruturado por IA local e análise da evolução clínica. Este guia reúne o que foi feito, como ligar o sistema e um roteiro para apresentá-lo ao orientador.

Autores: Gabriel Henrique Pereira Guimarães e Bruno Cheres de Oliveira Cruz. Orientador: Prof. Márcio Augusto de Souza.

Situação do projeto

O sistema está completo para o TCC. Todos os requisitos funcionais (RF01 a RF10) foram implementados e testados, os quatro experimentos têm resultados, e o texto (102 páginas, modelo da UEPG) não tem pendências.

O que ficou de fora está declarado no TCC como limitação ou trabalho futuro:

  • Implantação no servidor da UEPG. A configuração com seis contêineres foi validada numa máquina virtual do Azure, com dados sintéticos (veja Versão online), mas não no servidor da universidade. Por isso só o RNF02 aparece como “parcial”.
  • Teste com usuários. A usabilidade foi avaliada sem participantes (acessibilidade automática, KLM e avaliação heurística). O protocolo com acadêmicos e professores está no Apêndice e depende de aprovação ética.
  • Dados sintéticos. Casos clínicos, narrativas (escritas pelos autores), áudio (voz sintética) e coorte são fictícios. Nenhum dado real de paciente foi usado.
  • Um único modelo de linguagem (qwen2.5:3b), limitado pela falta de GPU. Segundo fator de autenticação (TOTP) não implementado.

O que foi feito

O trabalho foi dividido em seis fases. Cada uma gerou código testado e uma parte do texto.

FaseEntregas
1. Ficha como esquemaA ficha em papel virou um esquema JSON versionado: 144 campos, questões 1 a 75, com a forma de captação de cada seção (formulário, componente visual, ditado ou decisão exclusivamente humana). 40 casos clínicos sintéticos com gabarito.
2. API e bancoAPI em Node.js (Fastify) e PostgreSQL 17 com modelo híbrido (colunas + JSONB). Papéis aluno, professor, pesquisador e administrador; Row-Level Security; CPF, telefone e endereço cifrados; ficha aprovada imutável com adendos; trilha de auditoria; esquema analítico pseudonimizado.
3. InterfaceReact: formulário gerado a partir do esquema, mapa de palpação, odontograma FDI, fluxo de revisão do professor, administração e auditoria, tema claro e escuro, layout para tablet.
4. IA localTranscrição com Whisper e estruturação com Qwen2.5 pelo Ollama, na própria máquina. Cada sugestão vem com o trecho do relato que a justifica e é aceita ou rejeitada individualmente. Salvaguardas descartam valores sem evidência. As seções de diagnóstico nunca chegam ao modelo.
5. Módulo analíticoServiço em Python (FastAPI, Pandas, SciPy): intensidade da dor, GCPS, abertura bucal, palpação; testes de Wilcoxon e Kruskal-Wallis; painéis de evolução do paciente, da coorte e de qualidade; exportação CSV pseudonimizada.
6. Avaliação e acabamentoExperimentos A a D, benchmark JSONB × normalizado, revisão de segurança (2 defeitos reais corrigidos), auditoria de acessibilidade, KLM, avaliação heurística, implantação com contêineres (escrita).

Versão online

O sistema está implantado, só com dados sintéticos, numa máquina virtual do Azure (2 vCPUs, 8 GB de RAM, sem GPU), com HTTPS válido. Para mostrar, basta abrir o endereço e entrar com os usuários de teste; não é preciso ligar nada no computador.

Endereço
https://prontuario-lord.chilecentral.cloudapp.azure.com
  • Ligar e desligar: no portal do Azure, máquina virtual prontuario-lord → Iniciar ou Parar. Os serviços sobem sozinhos 1 a 2 minutos depois de iniciar. Parada, a máquina quase não consome o crédito de estudante.
  • Antes de apresentar: confira se a máquina está ligada (o desligamento automático pode tê-la parado) e faça uma chamada de aquecimento da IA; a primeira leva cerca de 2 minutos.
  • Atualizar o código: os comandos estão na seção “Implantação” do README.md.
  • Nunca cadastre dados reais nessa instalação: os usuários de teste têm senha conhecida.

Como ligar tudo

Pré-requisitos (uma vez)

  • Node.js 22 ou mais recente, Python 3.11 e Git.
  • Ollama instalado (ollama.com). Ele fica rodando em segundo plano, com ícone na bandeja do Windows.
  • Nenhum PostgreSQL precisa ser instalado: a API usa um banco embutido.

Instalação (uma vez)

Todos os comandos abaixo são para o PowerShell, a partir da pasta prontuario-lord.

Dependências JavaScript
npm install
Ambiente Python e serviços
py -3.11 -m venv .venv
.venv\Scripts\python -m pip install -r ferramentas\requirements.txt
.venv\Scripts\python -m pip install -e "services/analitico[figuras,testes]"
.venv\Scripts\python -m pip install -r services\transcricao\requirements.txt
Modelo de linguagem (cerca de 1,9 GB)
ollama pull qwen2.5:3b

O modelo de transcrição do Whisper (small) é baixado automaticamente no primeiro uso do ditado por áudio.

Subir o sistema (quatro terminais)

Abra quatro janelas do PowerShell na pasta prontuario-lord, uma para cada serviço, e deixe-as abertas durante a demonstração. Confira também se o Ollama está aberto.

1. API e banco

Sobe o PostgreSQL embutido, aplica as migrações e cria os dados de teste.

npm run dev -w @lord/api

2. Interface

Depois, abra http://localhost:5173 no navegador.

npm run dev -w @lord/web

3. Serviço analítico

Necessário para os painéis.

.venv\Scripts\python -m uvicorn app:app --app-dir services/analitico --host 127.0.0.1 --port 8766

4. Transcrição

Necessário só para gravar áudio no ditado.

.venv\Scripts\python -m uvicorn app:app --app-dir services/transcricao --host 127.0.0.1 --port 8765
Primeira execução. Na primeira vez, a API cria o banco, 12 pacientes sintéticos e a coorte de 150 pacientes (um contador aparece no terminal). Espere a mensagem “API de desenvolvimento em http://localhost:3333” antes de abrir a interface. Nas próximas vezes, ela sobe em segundos.

Conferir se está tudo no ar

Abra estes endereços no navegador; cada um deve responder sem erro:

Desligar e problemas comuns

  • Para desligar, use Ctrl+C em cada terminal.
  • Se a API não sobe porque a porta do banco ficou presa (depois de fechar uma janela à força):
npm run dev:parar -w @lord/api
  • Painel mostra erro de “serviço analítico indisponível”: o terminal 3 não está rodando.
  • “Gerar sugestões” demora ou falha: confira se o Ollama está aberto. A primeira chamada carrega o modelo e é mais lenta; sem GPU, cada seção leva de 35 s a 2 min.
  • Para voltar o banco ao estado inicial, feche a API e apague a pasta apps/api/.dados-dev; na próxima execução tudo é recriado.

Roteiro da demonstração

Cerca de 25 minutos. A ordem segue a vida de uma ficha: do cadastro à análise. Os trechos em itálico são sugestões do que falar.

Antes de começar

  • Os quatro terminais e o Ollama estão rodando, e os endereços de conferência respondem.
  • Faça uma chamada de aquecimento da IA (uma sugestão qualquer) uns minutos antes, para o modelo já estar carregado.
  • Deixe o PDF do TCC aberto (tcc-uepg-latex/tcc.pdf) para mostrar tabelas e figuras.
  • Tenha um relato curto pronto para colar no ditado (sugestão no passo 4).
  1. O problema e a ficha2 min

    Mostre a ficha em papel (Anexo do TCC) e o Quadro 3 (forma de captação por seção).

    A ficha tem 75 questões. Classificamos cada seção: respostas fechadas vão para formulário, exame para componentes visuais, relatos para ditado, e diagnóstico é só humano.

  2. Cadastro do paciente3 min
    aluna@lord.dev
    • Pacientes → Novo paciente → preencha nome e data de nascimento (CPF e telefone são opcionais) → salve.
    • Na tela do paciente, clique em “Registrar TCLE assinado hoje” e depois em “Novo atendimento”.

    CPF, telefone e endereço são gravados cifrados; a busca por CPF usa um índice HMAC, sem guardar o CPF em texto.

  3. Preenchimento da ficha4 min
    • Mostre a navegação lateral com a contagem de campos por seção e os números das questões do papel.
    • História médica: marque “usa medicamento: sim” e veja o campo de medicamentos aparecer (campo condicional).
    • Questionário de dor: régua de 0 a 10. Exame clínico: mapa de palpação e a tabela equivalente.
    • Seção “Eixo I”: marcada como clínica, sem painel de IA.
    • Troque o tema no cabeçalho (claro/escuro).

    O formulário é gerado a partir do esquema JSON. Se a Liga mudar a ficha, criamos uma versão nova do esquema e as fichas antigas continuam válidas.

  4. Ditado com IA5 min
    • Na seção História médica, abra “Ditado com IA”, cole o relato abaixo e clique em “Gerar sugestões” (cerca de 1 min).
    • Mostre que cada sugestão traz o trecho do relato entre aspas. Rejeite a que veio do comentário irrelevante (vestibular) e aceite as demais uma a uma.
    • Abra “Ver o que foi descartado automaticamente” para mostrar as salvaguardas.
    Relato de exemplo
    Trabalha como motorista de aplicativo. Fez uma restauração há quatro meses. Tem gastrite. Não fuma, não bebe e não usa drogas. Toma metformina 850 mg faz seis meses. Acorda várias vezes à noite. Nega ansiedade ou depressão. Nunca fez cirurgia e não tem alergia. Contou que a filha passou no vestibular.

    A IA roda na máquina, sem enviar nada para fora. Ela não diagnostica: as seções clínicas nem chegam ao modelo. E não existe “aceitar tudo”: tiramos esse botão porque a avaliação heurística mostrou que ele permitia aceitar sem ler.

    Se quiser mostrar o áudio: clique em “Gravar áudio”, fale o relato, pare e confira a transcrição antes de gerar.

  5. Envio e revisão do professor3 min
    • Clique em “Enviar para revisão”: o sistema avisa quantos campos obrigatórios faltam e pede confirmação.
    • Saia e entre como professora@lord.dev. Abra a ficha na fila, devolva com um comentário.
    • Volte como aluna, veja o comentário, corrija e reenvie. Como professora, aprove.
    • Mostre que a ficha aprovada fica somente leitura, com “Registrar adendo”.

    A imutabilidade é garantida por um gatilho no banco: nem o dono das tabelas altera uma ficha aprovada.

  6. Evolução do paciente2 min
    coorte@lord.dev

    Abra “Paciente Coorte C023”: variação da dor, gráficos por consulta com o tratamento sombreado, tabela com a GCPS e o mapa de palpação de cada consulta.

    Os indicadores são calculados por fórmula, sem IA. A GCPS segue o protocolo de pontuação do manual do RDC/TMD.

  7. Painel da coorte e pesquisa2 min
    pesquisadora@lord.dev

    Painel: redução da dor por tratamento, testes estatísticos, abandono. Mostre o botão “Exportar dados (CSV)”.

    A pesquisadora só enxerga dados pseudonimizados. Na coorte sintética, o sistema recuperou os efeitos que programamos (40%, 25% e 10% → 38,0%, 24,0% e 5,2%).

  8. Administração e auditoria1 min
    admin@lord.dev

    Trilha de auditoria: cada leitura e alteração que você fez na demonstração aparece aqui, sem dados clínicos.

  9. Resultados no TCC3 min

    No PDF, mostre o Quadro 9 (atendimento dos requisitos) e as tabelas dos experimentos, resumidas na seção Resultados deste guia. Feche com as limitações.

Se a IA estiver lenta ou falhar, mostre a Figura 11 do TCC (revisão das sugestões), que foi gerada com o modelo real, e siga o roteiro. Se o painel falhar, confira o terminal 3.

Resultados

Experimento A: estruturação por IA

30 casos de teste, modelo qwen2.5:3b, estratégia de ficha inteira.

SaídaF1AlucinaçãoOmissão
Bruta0,5932%20%
Com salvaguardas0,5525%34%

100% das respostas respeitaram o esquema. A extração por seção teve F1 parecido (0,58), mas alucinação de 69%. Erros típicos: listar opções que o paciente não citou, negação de uma frase contaminando a vizinha e “ponte móvel” registrada como prótese total.

Experimento B: áudio versus texto

Voz sintética pt-BR, Whisper small, 30 narrativas.

CondiçãoPalavras erradas (WER)Pior caso
Silêncio4,0%9,0%
Ruído simulado (10 dB)6,2%14,0%

Em 10 casos, o F1 da estruturação caiu de 0,59 (texto) para 0,56 (áudio), e de 0,56 para 0,47 com as salvaguardas.

Experimento C: usabilidade sem participantes

  • Acessibilidade (axe-core, WCAG 2.1 AA): 3 violações sérias encontradas e corrigidas; depois, zero em 10 telas nos dois temas.
  • KLM: ficha completa pelo formulário em cerca de 9,7 min. Revisar sugestões reduz a interação em 15%, mas a espera pelo modelo, sem GPU, anula o ganho.
  • Avaliação heurística: 8 problemas; 3 corrigidos (aceite em lote removido, aviso ao enviar ficha incompleta, rótulo da completude).

Experimento D e avaliação técnica

  • Coorte sintética de 150 pacientes: os intervalos de confiança contêm os efeitos programados; banco e gerador dão o mesmo resultado.
  • Benchmark com 10.000 pacientes: JSONB lê o prontuário 3 a 4 vezes mais rápido e leva 40–45% menos tempo para gravar um atendimento que o modelo normalizado, ocupando quase metade do disco.
  • Segurança: 37 testes de ataque; 2 defeitos reais corrigidos (tela em branco com a política de segurança de conteúdo; erro 400 antes do 401); nenhuma vulnerabilidade conhecida nas dependências.
  • OWASP ZAP sobre a versão online: nenhum alerta de risco alto; injeção de SQL, XSS e demais ataques ativos passaram. Os alertas médio e baixos da varredura passiva foram corrigidos; resta a identificação do nome do servidor intermediário (Caddy), aceita como risco residual.

Perguntas prováveis

Por que um modelo tão pequeno?

Porque os dados não podem sair da instituição e não havia GPU. Um modelo de 3 bilhões de parâmetros em CPU já leva cerca de dois minutos por relato. Modelos maiores ficam para o servidor com GPU.

F1 de 0,59 não é baixo?

É suficiente para sugerir e insuficiente para dispensar revisão, e é por isso que o sistema obriga a revisão campo a campo. A medida automática também subestima os campos de texto, porque penaliza paráfrases corretas.

A IA pode dar diagnóstico?

Não, por construção: as seções de diagnóstico e plano de tratamento são marcadas no esquema, não são enviadas ao modelo, e a API recusa sugestões para elas. Há testes automatizados para isso.

Por que não houve teste com usuários?

Dependia de voluntários da Liga e de aprovação do Comitê de Ética, que não couberam no prazo. A usabilidade foi avaliada por três métodos sem participantes, e o protocolo com usuários está no Apêndice.

Por que dados sintéticos?

Para não usar dados reais sem autorização e para ter gabarito: sabendo o que devia ser extraído e o efeito programado na coorte, dá para medir o erro exatamente.

O sistema substitui o prontuário em papel?

Ainda não. A Lei 13.787/2018 exige certificado ICP-Brasil para a validade legal do documento digital. Isso está nos trabalhos futuros.

Por que JSONB e não um modelo totalmente relacional?

O benchmark mostrou leitura 3 a 4 vezes mais rápida, gravação com 40–45% menos tempo e quase metade do espaço. O relacional só ganhou na consulta analítica sobre todas as fichas, que roda fora das telas clínicas.
